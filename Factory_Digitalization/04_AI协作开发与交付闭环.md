# AI 协作开发与交付闭环：从任务拆分到用户真正用上

## 中文

本文复核一次六任务并行升级的任务交接、集成记录、测试回执及后续发布报告。项目身份和内部地址已移除，保留候选失败到限定交付的先后关系。测试数量用于说明范围，不作为完成度评分。

## 1. 为什么拆开工作之后，项目仍可能没有完成

一项升级可能同时涉及使用说明、公开入口、功能基线、计算修复、性能和集成。每部分看起来都能分给不同执行者，但它们并不独立：修复需要可靠基线，公开入口需要访问边界，性能比较需要固定场景，最终交付需要兼容的产物。

因此，任务拆分的第一张表应是依赖表，而不是人员分配表。

| 工作 | 输入条件 | 可接收产物 | 不能替代的后续结果 |
|---|---|---|---|
| 功能基线 | 固定样本与预期 | 可重复的现状记录 | 不能代表修复成功 |
| 功能修改 | 可用契约与基线 | 代码、说明及定向检查 | 不能代表已安装 |
| 性能优化 | 固定环境和场景 | 同条件前后对比 | 不能代表所有场景更快 |
| 公开入口 | 身份、隔离和使用条件 | 可检查的用户路径 | 不能代表分发条件齐全 |
| 集成发布 | 可配套的模块产物 | 运行版本及业务回执 | 不能靠构建结果代替 |

## 2. 案例一：并行任务各有进展，最终验收却没闭合

### 早期进展为什么容易令人乐观

多个执行者完成文档整理、界面拆分、测试脚本和局部优化。协调者收到许多提交、构建结果和绿色检查，容易把“成果已收拢”理解为“升级快完成了”。

进一步逐项复核，却发现正式的自主任务评测没有走通，某个验收器连自制标准样本也判失败，一部分计算修复没有交付，公开使用条件仍有缺口。

局部成果是真实的，整体未完成也是真实的。复盘应同时保留两者。

### 三类问题需要分别处理

第一类是评测接线失败，例如返回格式不匹配或执行链中断。它阻塞的是对应评测，不自动证明产品失败。

第二类是验收器错误。需要先检查已知样本、判断条件和环境，再用它评价产品。

第三类是尚未完成的业务或产品工作。即使前两类修好，这些工作也不会自动消失，仍要逐项继续。

把三类都写成“测试中”，会让使用者无法判断下一步需要修什么。

### 怎样把任务接回来

需要集中处理时，先停止原执行者，记录最后产物、工作位置、未完成项和在途任务，再由一个明确的集成负责人继续。

接管不只是复制文件。要确认原执行者不再继续写、候选版本可构建、验证使用的是同一版本，以及后续完成条件没有被缩减成更容易的局部检查。

### 一次六任务拆分的实际依赖

这次升级分为来源与许可、公开版边界、Agent 评测、几何修复、性能、自身集成发布六条工作线，分别放在独立 worktree。几何修复依赖可靠的失败样本；集成发布依赖前面可配套的候选。因此，有些执行者只能先做只读准备，而不是六人同时修改六个完全独立模块。

集成记录留下了两个容易被“各自完成”掩盖的问题。第一，一项性能分支携带了公开版分支已经包含的补丁，接管时明确排除重复应用。第二，发布校验脚本出现冲突：一侧增加许可拒绝门禁，另一侧增加公开版/集成版资产边界。解决方式是保留两组约束，不能选“保留本分支版本”就算合并完成。

主会话后来停止六个执行者，在既有集成 worktree 接管，记录各提交的来源与集成对应关系。两种候选均构建通过，部分浏览器和导出回读通过；但这一轮最终记录仍明确 `notOverallComplete=true`。

| 当时已有的证据 | 为什么没有闭合原目标 |
|---|---|
| 20 道题中 11 道完成固定步骤建模与导出回读 | 自主模型通道曾因上游要求流式请求而返回 HTTP 400，未产生页面写入；固定步骤不能替代自主规划 |
| 独立几何读取器及数学检查 | 一项复合模型检查连参考几何也给出矛盾的布尔差集，不能据此要求产品修形 |
| 两种候选构建及局部持久化通过 | 匿名计算隔离、完整性能范围、分发材料及真实部署仍有缺口 |
| 几何修复工作线有准备记录 | 未交付内核修复；不能把“等待基线”算成产品已修复 |

这不是“并行无效”，而是集成阶段的输入尚未满足：评测链不能提供可信失败，几何修复就没有可靠靶点；候选包不能提供现场版本，用户就不会自动用上它。

### 后续怎样形成一次有边界的交付

后续恢复工作保留原题库与失败证据，没有重新把六条工作线全部推倒。发布报告记录了原题的模型、工具及独立几何结果，最后五题由原生 Codex 执行者完成，并补了基础题和冷重开验证。这里不能偷换成“原来的远端 Agent 通道全部通过”：执行通道发生了明确变化，报告说明未使用原远端 Agent。

最终交付还补齐实际公开页面和配套计算服务，用两个独立访客验证任务及产物隔离、重复提交返回原作业、真实计算完成及产物哈希；工程恢复检查保留对象数、体积、位置与外观。页面入口、知识包、源码包与运行身份分别核对，部署回执才能与源码提交连起来。

后续发布解决的是该轮限定范围。性能检查仍只覆盖指定设备与场景，原生内核重编和逐字节重现未执行；之后的更复杂长建模任务仍有独立未完成项。把早期失败永远写成当前状态，或把后续局部发布扩大成全部能力验收，都是时间线错误。

自动检查器及冷恢复的几何机制集中见[第 05 篇](05_AI_CAD的几何验证与恢复.md)；本篇关注的是谁接收依赖、如何合并约束，以及哪份证据允许阶段状态向前移动。

## 3. AI 与人分别负责什么

AI 适合调查独立模块、生成实现、整理差异、执行定向检查和汇总阻塞。人明确业务优先级、决定范围变化、判断使用结果和接受未完成风险。

协调角色负责输入版本、接口契约、共享文件、依赖顺序及最终接收。这个角色可以使用 AI 辅助，但不能只负责转发各子任务“已完成”的消息。

“调查一下”“写需求”“实施并发布”是不同任务。技术上可以继续做，不等于当前已经授权继续做。任务说明应在开始时明确本轮结束于哪一种产物。

## 4. 发布账本：清单不能由开发目录代替

### 出现了什么问题

以下是发布记录复核中需要防止的机制，不把尚未逐文件复现的清单漂移另算一个成功修复案例。局部功能更新只计划安装少量文件，工作区却同时存在其他改动。发布后重新生成整目录清单，可能把未上传的本地文件也记为服务器已有。

这样下一次比较时，系统会误以为这些文件不需要发布，形成“清单正确、现场错误”的假象。

### 怎样核对

将本次允许安装的文件、实际传输记录和目标环境内容逐项对应。清单应记录实际部署状态，而不是简单复制开发目录的现状。

如果清单已误写，可以依据此前清单和本次真实成功记录重建；没有现场证据的文件，应标为待核对，而不是猜测它已经更新。

可以进一步设计安装后再更新发布账本的流程，但本文不把这种改进建议当作已有实现。

## 5. 案例三：按钮已发布，依赖服务还是旧版本

一个转换功能的界面已经上线，本地样本也通过，生产端却缺少对应计算组件。用户看到入口，最终仍拿不到产物。

这里应先确认失败阶段：请求是否发出、目标服务是否可用、版本和契约是否配套、产物能否读取。问题在运行组合，不一定需要再次修改前端。

修正时补齐实际缺少的服务和配置，对已一致的组件不重复覆盖。使用代表性输入走完真实调用与产物读取，才能说明这条使用路径已经恢复。

这类发布可以用“业务目标—源码版本—产物清单—安装位置—运行版本—结果回执”连接起来。组件数量增加后，版本对应关系比“都已更新”这句话更重要。

## 6. 验收范围要跟着风险走

小型文字或布局修改，检查直接受影响的区域即可。参数契约改变，要核对调用方和被调用方。涉及真实写入，要检查身份、关联状态和回读。影响保存结构，要验证重开或回读。

不必每次进行全站审计，但也不能用无关测试数量代替关键业务路径。只有新修改、具体失败或未解决问题，才应触发额外检查。

性能结果需要记录样本、环境、配置和测量方式。某个大场景改善，不代表小场景、不同设备或其他模型都会改善。

## 7. 把交付拆成可核对的状态

建议在最终说明中分别写：

- 已实现：哪些行为变化，采用什么方法；
- 已验证：哪些样本和检查通过，覆盖范围是什么；
- 已保存版本：怎样追溯本次变更；
- 已安装：目标环境实际使用什么产物；
- 已验收：哪个真实任务得到什么结果；
- 未完成：缺口、阻塞、影响和下一步。

本地构建、版本保存、远端发布和业务验收之间没有自动等号。没有到达的阶段明确写出来，比用一个“完成”隐藏差异更便于继续工作。

## 8. 可复用的任务与交接格式

开始前写目标、范围、输入版本、依赖、允许动作、产物和完成条件。结束时对照原目标列出证据，而不是按执行过程罗列工具调用。

交接材料至少保留当前候选、有效与失败样本、实际运行状态、未完成项和可直接执行的下一步。临时推测与已确认事实分开写，避免下一位执行者把猜测当成设计前提。

并行开发的价值在于缩短独立工作的等待时间。它需要集成能力、可靠证据和持续推进，不能仅靠增加执行者数量获得。

# AI Collaboration and Delivery: From Task Division to Usable Results

## English

This article revisits a six-task parallel upgrade through handoffs, integration records, test receipts, and a later release report. Project identities and internal addresses are removed, while the chronology from incomplete candidates to scoped delivery is preserved. Test counts describe scope rather than completion scores.

## 1. Why divided work can remain unfinished

An upgrade can include instructions, public access, a baseline, computation fixes, performance, and integration. These tasks depend on each other. Fixes need reliable baselines, public access needs boundaries, comparisons need fixed scenarios, and delivery needs compatible artifacts.

Map dependencies before assigning executors.

| Work | Required input | Acceptable output | What it does not establish |
|---|---|---|---|
| Baseline | Fixed samples and expectations | Repeatable current-state record | Successful repair |
| Functional change | Contract and baseline | Implementation, instructions, targeted checks | Installation |
| Performance | Fixed environment and scenario | Comparable measurements | Universal improvement |
| Public access | Identity, isolation, usage conditions | Checkable user path | Complete distribution compliance |
| Integrated release | Compatible module artifacts | Runtime version and business receipt | Something proven by a build alone |

## 2. Case one: local progress without complete acceptance

### Why early progress looks convincing

Executors deliver documentation, interface changes, test scripts, and local optimizations. The coordinator receives many saved versions and green checks and assumes that collecting the outputs means the upgrade is nearly done.

A requirement-by-requirement review reveals a different picture: formal autonomous evaluation has not worked, an evaluator rejects its own known sample, some computation fixes remain absent, and public use conditions are incomplete.

The local results have value, and the overall project remains unfinished. A useful review preserves both facts.

### Treat three problem classes separately

Evaluation wiring can fail through incompatible response formats or interrupted execution. That blocks the evaluation; it does not automatically prove a product defect.

An evaluator can be defective. Validate samples, conditions, and environment before relying on it.

Some work is simply not implemented. Fixing evaluation infrastructure does not complete missing product requirements.

Calling all three “testing in progress” hides the next action.

### Centralize work deliberately

When work returns to one executor, stop previous executors, record their latest outputs, locations, open work, and in-flight tasks, then assign integration ownership.

Copying files is insufficient. Confirm that old executors are no longer writing, the candidate builds, checks use the same version, and acceptance has not been reduced to an easier local milestone.

### The actual dependencies in a six-task split

The upgrade separated provenance and licensing, public-edition boundaries, Agent evaluation, geometry repair, performance, and release integration into independent worktrees. Geometry repair depended on credible failing samples; integration depended on compatible candidates. Some executors could therefore only prepare read-only work, rather than all six changing independent modules simultaneously.

Integration records preserved two problems hidden by individual completion messages. A performance branch carried a patch already present in the public-edition branch, so takeover explicitly excluded duplicate application. A release-check script also conflicted: one side added a fail-closed licensing gate, the other public/integrated asset boundaries. Resolution preserved both constraints instead of simply accepting one branch's version.

The parent session later stopped the six executors and took over the existing integration worktree, mapping source commits to integrated commits. Both candidates built, and some browser and export-readback checks passed. The final record for that round nevertheless explicitly retained `notOverallComplete=true`.

| Evidence already available | Why the original goal remained open |
|---|---|
| Fixed-step modeling and export readback for 11 of 20 cases | An autonomous-model attempt received HTTP 400 because the upstream required streaming; no page writes occurred. Fixed steps did not establish autonomous planning |
| Independent geometry reader and mathematical checks | A composite-model checker produced contradictory Boolean differences even for reference geometry; it was not a reliable basis for changing the product |
| Two candidate builds and partial persistence checks | Anonymous compute isolation, full performance scope, distribution evidence, and deployment remained incomplete |
| Geometry-repair preparation | No kernel repair had been delivered; waiting for a baseline was not a completed fix |

Parallelism itself was not disproved. Integration inputs were missing: without trustworthy evaluation failures, repair had no reliable target; without installed runtime identity, users did not automatically receive a candidate's behavior.

### How a later scoped delivery was established

Recovery retained the original task set and failing evidence instead of restarting all six workstreams. The later release report recorded model, tool, and independent geometry outcomes for the original cases; native Codex executors completed the final five, followed by basic-task and cold-reopen checks. This must not become a claim that the original remote Agent channel passed everything. The execution channel changed, and the report explicitly excluded that remote Agent.

Delivery also included the actual public page and matching compute service. Two independent visitors tested task and artifact isolation, duplicate submission returning the original job, real computation, and artifact hashes. Recovery checks retained object count, volume, position, and appearance. Page entries, knowledge packages, source packages, and runtime identity were checked separately to connect deployment receipts to source commits.

The later release closed a defined scope. Performance measurements remained limited to particular devices and scenes; native-kernel rebuilding and byte-for-byte reproduction were not performed. Subsequent complex long-modeling tasks retained separate open requirements. Treating an early failure as permanent current state, or a later scoped release as universal acceptance, would both distort the chronology.

Geometry mechanisms behind the checker and cold recovery are covered in [Article 05](05_AI_CAD的几何验证与恢复.md). This article concerns ownership of dependencies, preservation of constraints during integration, and evidence that permits a delivery stage to advance.

## 3. Roles and authorization

AI is useful for independent investigations, implementation, difference analysis, targeted checks, and blocker summaries. People set business priorities, authorize scope changes, judge user outcomes, and accept outstanding risk.

Coordination owns input versions, contracts, shared files, dependencies, and acceptance. It may use AI, but cannot consist only of forwarding completion messages.

Investigation, requirements, implementation, and deployment are different assignments. Technical ability to continue is not authorization to continue. State the required final artifact at the start.

## 4. Release Ledgers Must Not Stand In for Installed State

The following mechanism is a release-review concern, not an additional successful repair claimed without file-level reproduction. A small update installs selected files while unrelated changes remain locally. Regenerating a whole-directory manifest can incorrectly mark uninstalled files as present in production.

A later comparison may then skip required files because the ledger claims they are current.

Correlate the permitted file list, actual transfer receipts, and target content. The manifest should describe deployed state, not simply copy the development directory.

If the record is wrong, reconstruct it from the previous manifest and confirmed transfers. Mark uncertain files for inspection rather than assuming installation. Updating the ledger only after successful installation is a possible improvement, not an implementation claim made here.

## 5. Case three: a published button depends on an outdated service

A conversion interface is deployed and local samples work, but production lacks the matching computation component. Users see the action and still receive no artifact.

Locate the failure: request submission, service availability, compatible contracts and versions, or artifact retrieval. The runtime combination may be wrong without requiring another interface change.

Install the missing dependencies and configuration without repeatedly overwriting components already confirmed current. Complete a representative request and artifact read through the actual user path.

Connect the goal, source version, artifact list, installation location, running version, and result receipt. As component counts grow, that relationship matters more than “everything is updated.”

## 6. Match acceptance to impact

A small text or layout change needs a focused check. Contract changes require both caller and receiver checks. Real writes need identity, related state, and readback checks. Changes to saved structures need reopen or readback verification.

A full audit is not always necessary, but unrelated test counts cannot replace a critical business path. Extend checks when new changes, concrete failures, or unresolved concerns justify it.

Performance reports should include sample, environment, configuration, and measurement method. One improved large scenario does not establish improvement across devices and workloads.

## 7. Report delivery states separately

State what was implemented, which samples were checked, how the version is recorded, what was installed, which real task passed acceptance, and what remains.

Builds, saved versions, publication, and business acceptance are not equivalent. Naming an unfinished stage is more useful than hiding it under a single completion label.

## 8. Reusable task and handoff records

At the start, record the goal, scope, input version, dependencies, allowed actions, deliverables, and acceptance criteria. At the end, compare evidence with the original goal rather than listing tool activity.

Handoffs should preserve the current candidate, successful and failing samples, actual runtime state, outstanding requirements, and an executable next step. Separate hypotheses from confirmed facts.

Parallelism reduces waiting for independent work. It still needs integration capacity, reliable evidence, and continued execution; adding executors alone does not provide those properties.

# AI 完成开发之后，怎样确认交付

## 中文

## 代码、产物与运行环境可能不同步

源文件已修改，不代表安装产物已更新；产物已上传，不代表运行服务正在使用；页面已发布，也不代表其依赖服务具备配套能力。

确认交付，需要把业务目标与用户真正使用的版本联系起来。

## 通用案例：界面已更新，计算服务仍是旧版

某应用新增转换功能，界面已经出现入口，本地样本也成功，但生产环境没有同步依赖服务。用户能看到按钮，却无法得到完整产物。

排查时，分别核对界面、服务、配置和知识说明，再补齐实际缺失的组件。对已经一致的内容，无需为了“全量更新”重复覆盖。最后用代表性输入执行转换并读取产物，确认真实路径。

另一个常见问题是发布清单误记：本地还有无关修改时，不能将所有当前文件都标成已经上线。

## AI 怎样参与

AI 可以整理受影响文件、构建产物、比较版本、协助部署、读取运行状态并执行定向检查。人确认发布范围、业务影响和可接受结果。

所有步骤沿用已明确的授权边界。发布工具和环境可以不同，记录应始终能说明本次改变了什么、用户在哪里使用它。

## 把状态写具体

| 状态 | 证明范围 |
|---|---|
| 本地已实现 | 对应源文件或资源已修改 |
| 检查通过 | 指定检查覆盖范围内结果符合预期 |
| 版本已保存 | 指定变更进入可追溯版本 |
| 已安装运行 | 目标环境正在使用对应产物 |
| 业务验收通过 | 指定真实路径得到预期结果 |

文件校验一致只能证明内容相同；成功调用只能证明该样本走通。两者都有价值，但不应扩展为全部业务均已验证。

## 可复用的交付记录

保留业务目标、变更范围、来源版本、实际安装内容、目标环境、恢复办法、直接成功确认及剩余事项。

普通小改动完成与影响直接相关的检查即可。跨服务契约变化，应核对两端并执行代表性流程。发生具体错误后，再补针对性检查。

排障时按源文件、产物、安装、配置、运行路径和业务结果定位，能减少重复发布，也让下一位执行者知道真正剩下哪一步。

# Confirming Delivery After AI-Assisted Development

## English

## Source, artifacts, and runtime can diverge

Changed source does not prove that installation artifacts are current. Uploaded artifacts do not prove that a running service uses them. A published interface may depend on a service that has not been updated.

Delivery connects the business goal to the version users actually run.

## Generic example: a new interface with an old processing service

An application introduces a conversion feature. The interface is visible and a local sample succeeds, but the production dependency is still outdated. Users see the action without receiving the expected artifact.

Check the interface, service, configuration, and instructions separately. Update missing components without repeatedly overwriting content that already matches. Run a representative conversion and read the resulting artifact through the actual user path.

Release records can also be wrong. Unrelated local changes must not all be marked as deployed.

## How AI participates

AI can identify affected files, prepare builds, compare versions, assist deployment, inspect runtime state, and run targeted checks. People confirm scope, business impact, and acceptable results.

Use established authorization boundaries. Release tools and hosting environments may vary, but the record should explain what changed and where users access it.

## Describe delivery states precisely

| State | What it establishes |
|---|---|
| Implemented locally | Relevant source or resources changed |
| Checks passed | Results met expectations within specified checks |
| Version recorded | Changes belong to a traceable version |
| Installed and running | The target environment uses the intended artifacts |
| Business acceptance passed | A specified real workflow produced the expected result |

Matching file checks establish identical content. A successful invocation establishes success for that sample. Neither proves that all business behavior has been verified.

## Reusable delivery record

Record the goal, change scope, source version, installed content, target environment, recovery method, direct confirmation, and outstanding work.

Small changes need checks related to their impact. Cross-service contract changes need both ends checked and a representative workflow. Expand verification when an actual error warrants it.

Locate failures across source, artifacts, installation, configuration, runtime path, and business outcome. This reduces repeated releases and makes the remaining work clear to the next executor.

# 知识工程与人机分工：让业务经验成为可执行的方法

## 中文

本文的案例由开发与复核问题抽象而来，已改变业务对象与表达方式，不包含真实组织、数据或实现细节。文中的候选方案是可复用的设计思路，不代表所有机制已经实施。

## 1. 为什么资料越多，助手仍可能做错

给助手更多文件，未必能让它判断更稳定。资料里可能同时存在旧规则、新口径、个别样本和未确认猜测；即使每份文件都写得通，组合后也可能冲突。

更关键的是，资料通常只回答“知道什么”，执行还需要回答“现在该用哪个规则”“缺什么就暂停”“结果怎么检查”。因此，知识库的建设不能以文件数量为目标，应围绕具体任务建立读取和判断路径。

## 2. 案例一：估价知识更新后，旧假设为什么还在生效

### 起初的做法

团队已有核心规则、历史估价和专项参考。收到一批新经验后，最省事的做法似乎是再写一份“补充说明”，要求助手优先阅读。

这样很快会出现多个入口：核心文件保留旧默认值，新表格使用新值，补充说明又有一组例外。不同检索路径可能得到不同答案。把所有文件一次性塞给模型，也只是把冲突搬进上下文。

### 先确认规则的性质

整理时先把材料分成四类：

| 类型 | 例子 | 应怎样处理 |
|---|---|---|
| 稳定规则 | 费用项目如何组成 | 写入核心方法 |
| 有时效的参数 | 当期材料或汇率参考 | 带生效范围与更新时间 |
| 样本证据 | 某类产品的一次历史报价 | 留在参考资料，不直接泛化 |
| 已纠正假设 | 某类费用原来被遗漏 | 明确修正并处理旧文本 |

业务负责人确认的新口径可以覆盖旧假设，但不能把“某次结果如此”自动变成“以后都如此”。AI 在这里负责比较、归类和定位冲突，业务人员决定规则是否成立。

### 再决定文件怎样组织

保留稳定的任务入口，让核心规则保持简洁，大型参考表单独存放。入口写清何时读取某张表、采用什么单位、哪些字段需要现场确认。

更新时列一张变更清单：新增了什么、修改了什么、废止了什么、适用哪些任务。修改核心规则后，同时寻找其他文件中的旧表达，而不是只在末尾添加一句“以最新为准”。

### 怎样判断更新真的有效

用同一组任务比较更新前后：普通估价是否只读取必要资料；特殊结构是否进入正确参考分支；旧默认值是否还会出现；缺少当前参数时是否说明需要补充。

验证的是规则的实际使用路径，不只是文件格式和索引链接。知识内容正确但入口找不到，执行时仍然等于不可用。

## 3. 案例二：风险报告格式正确，为什么等级仍然不合理

### 发现反例

一个订单分析流程由程序整理交期、欠数和相关事项，再让模型从几个风险等级中选择。输出字段完整、枚举合法、引用也齐全，但已完成交付的订单仍可能因为历史未结事项被判为紧急。

这类错误无法靠检查输出格式解决。它说明业务优先级没有明确：当前交付事实和历史事项谁先影响结论？历史质量问题是否需要单独列示？什么情况必须进入人工复核？

### 把错误拆成可检查的部分

首先核对事实：交付完成指的是整单还是某个配件？数据是当前值还是旧缓存？模型引用的是本单还是同产品的其他记录？

随后核对规则：已完成是否可以排除交期风险？仍未关闭的问题属于另一种风险吗？资料不足时是否允许归为正常？

最后才调整模型输入与提示。如果事实粒度错误，仅强化提示词不会补出缺失的订单关联。

### 复用报表数据，但不直接套用报表结论

已有报表和缓存能减少重复取数。然而产品级汇总不等于订单级证据，部门积压估算也不一定能证明某张订单是否齐套。

合适的做法是复用数据采集与基础计算，同时为分析保留必要明细、关联标识、数据时间和估算标记。缺少的采购或外部处理数据另行补齐，不能把“无记录”直接解释为“无风险”。

### 重新安排程序与模型的工作

常规程序承担去重、关联、单位转换、稳定规则和候选筛选。模型接收候选摘要，解释矛盾、综合描述并提出行动建议。

初筛至少保留两类：明确命中风险，以及资料缺失或互相矛盾、仍需判断的对象。若只保留“已经证明有风险”的记录，最需要人判断的疑点可能被提前筛掉。

一个通用的分析输入可以包含：

- 对象及关联链；
- 当前状态和数据时间；
- 计算特征及命中原因；
- 相关证据引用；
- 缺失、矛盾和估算标记；
- 需要模型回答的问题。

完整流水可以保留在受控系统中，需要时再补读。摘要应减少无关信息，同时保留结论所需的证据链。

## 4. 反馈不是自动学习，写了评语也不等于改变算法

复核人员写“这条不应判紧急”，可能只是保存了一条评语。如果程序没有读取评语，规则未更新，后续输入也未包含修正，下一次仍可能做出相同判断。

反馈需要经过“记录反例—确认原因—决定改哪一层—更新—回归样本”这个过程。若问题来自数据关联，修数据处理；来自稳定业务优先级，补明确规则；来自语言理解，调整知识和模型任务。不要把所有问题都塞进一条越来越长的提示词。

还要保留新的例外，防止修复一个反例后过度排除其他真正高风险对象。

## 5. 怎样评估收益，而不靠感觉

比较旧方案与候选方案时固定样本和数据快照。观察漏报、误报、等级改判、人工复核时间、端到端耗时和模型使用成本。

输入变少不保证总成本降低。若摘要缺失关键证据，模型可能增加补读，人工也可能花更多时间追查。新系统应按完整任务衡量，而不只看单次模型请求。

如果只有需求与原型，就报告到需求与原型；如果缺少同样本对照，不应宣布准确率或节省比例。

## 6. 一份可以复用的知识变更记录

建议记录：任务、旧规则、发现的反例、已确认原因、新规则、适用范围、废止内容、入口、运行版本和验证样本。

这份记录帮助下一位执行者理解“为什么这样做”，也让后来出现冲突时有地方追查。知识工程的核心，是把经验变成能够被找到、正确使用、修正和验证的方法。

# Knowledge Engineering and Human–AI Work Allocation

## English

The cases below are generalized from development and review problems. Business objects and wording have been changed, and no organizational data or implementation details are included. Proposed mechanisms are reusable designs, not claims that every mechanism has been implemented.

## 1. Why more material does not guarantee better decisions

A knowledge collection can contain old rules, new definitions, individual examples, and unconfirmed assumptions. Each document may look reasonable while the collection remains contradictory.

Information answers what is known. Execution also needs to establish which rule applies now, what missing information requires a pause, and how the result is checked. Knowledge work should therefore organize a task's retrieval and decision path rather than maximize file counts.

## 2. Case one: an estimation update leaves old assumptions active

### The initial approach

A team maintains core rules, historical estimates, and specialized references. After receiving new experience, it creates another supplementary guide and asks the assistant to prioritize it.

This creates competing entry points. The core retains an old default, a table uses a new value, and a supplement adds exceptions. Different retrieval paths produce different answers. Loading everything together merely transfers the conflict into the model context.

### Classify the material first

| Type | Example | Treatment |
|---|---|---|
| Stable rule | How cost components combine | Maintain in the core method |
| Time-sensitive parameter | Current material or exchange-rate reference | Record validity and update time |
| Sample evidence | A historical estimate for one item | Preserve as a reference rather than a universal rule |
| Corrected assumption | A previously omitted expense | Correct it and address obsolete text |

A confirmed business rule can supersede an older assumption. A single observed outcome does not automatically become a permanent rule. AI compares, classifies, and locates conflicts; business owners determine validity.

### Organize the update

Keep a stable task entry point, concise core rules, and separate large reference tables. Explain when to load each reference, which units apply, and which values require current confirmation.

Record additions, changes, retirements, and scope. When changing a core rule, search for obsolete versions elsewhere. A final sentence saying “use the latest version” does not resolve competing instructions.

### Check actual use

Use the same tasks before and after the update. Does a normal estimate retrieve only relevant material? Does a special structure enter the right branch? Does the old default still appear? Does the assistant request missing current parameters?

These checks validate the execution path, not only formatting and links. Correct knowledge that cannot be found is unavailable in practice.

## 3. Case two: valid risk reports contain unreasonable classifications

### Find the counterexample

Software prepares delivery dates, outstanding quantities, and related issues. A model chooses among risk levels. Fields, enums, and references are valid, yet an already-delivered order is labeled urgent because of an unresolved historical issue.

Schema validation cannot resolve the missing business priorities. Should current delivery facts take precedence? Should historical quality issues appear separately? When must a case be reviewed by a person?

### Decompose the error

First check facts. Does completion refer to the whole order or one component? Is the information current or cached? Is the cited record linked to this order?

Then check rules. Does delivery completion remove delivery risk? Is an open issue a different risk category? Can incomplete information be classified as normal?

Only then adjust the prompt and model input. Stronger wording cannot repair missing order relationships.

### Reuse reporting data carefully

Existing reports and caches reduce repeated collection, but product totals do not establish facts for individual orders. Department backlog estimates may not prove order readiness.

Reuse collection and basic calculations while preserving required detail, relationships, timestamps, and estimate markers. Add missing purchasing or external-processing data. Absence of a record is not automatically absence of risk.

### Reallocate the work

Conventional software handles deduplication, relationships, units, stable rules, and candidate selection. The model receives candidate summaries, interprets contradictions, synthesizes descriptions, and proposes actions.

Retain both explicit risks and cases with missing or conflicting evidence. Filtering for proven risks alone can discard the cases most in need of judgment.

Useful inputs include the object and related chain, current state and timestamp, computed features, selection reasons, evidence references, uncertainty markers, and the question to be answered. Detailed histories can remain in controlled storage for selective retrieval.

## 4. Feedback does not automatically change the system

A reviewer comment may simply be stored. Unless the program reads it, a rule is updated, or a later input includes it, the same error can recur.

Use a cycle of counterexample, confirmed cause, layer selection, change, and regression sample. Repair relationships in data processing, stable priorities in explicit rules, and interpretation problems in knowledge or model instructions. Avoid putting every correction into an ever-growing prompt.

Retain boundary cases so that fixing one false alert does not suppress genuine risks.

## 5. Evaluate the complete task

Compare old and candidate approaches on fixed samples and data snapshots. Track missed risks, false alerts, reclassification, human review effort, end-to-end time, and model cost.

Smaller inputs do not guarantee lower total cost. Missing evidence can cause additional retrieval and more manual investigation. Measure the completed task rather than one model request.

Report requirements or prototypes as such. Without comparable measurements, do not announce improved accuracy or a savings percentage.

## 6. A reusable knowledge change record

Record the task, previous rule, counterexample, confirmed cause, replacement rule, scope, retired material, entry point, runtime version, and verification samples.

This preserves the reason behind a procedure and makes later conflicts traceable. Knowledge engineering turns experience into a method that can be found, applied, corrected, and checked.

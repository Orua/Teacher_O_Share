# 程序与大模型如何分工

## 中文

## 先分清计算与判断

当任务包含大量统计、比较和状态判断时，把全部数据直接交给模型未必合适。规则明确的处理可以由常规程序完成；需要解释、综合与处理不完整证据的部分，再交给模型。

这与具体编程语言无关，关键是规则能否明确表达和复核。

## 通用案例：订单风险分析

某风险分析流程先整理交期、欠交、采购及质量事实，再要求模型选择风险等级。输出结构和引用都合规，仍可能把已完成订单因历史事项判为高风险。问题在于缺少明确的优先级和排除条件。

调整时，先调查现有报表是否已有可复用数据，再补齐缺失来源。程序完成去重、关联、稳定规则判断和候选筛选，模型接收必要事实，解释风险、指出证据缺口并提出待核实问题。

汇总口径要特别小心：产品层面的库存或进度，不一定能证明某张订单已经完成。估算数据可以提供风险线索，但应标明适用范围。

## AI 怎样参与

AI 可以阅读数据说明和实现，帮助发现缺失来源、比较口径、整理规则草案，并解释候选异常。业务人员通过复核具体样本，确定哪些条件有优先权、哪些例外不能自动判断。

用户评语只有进入受控规则或后续输入，才会影响正式分析；不能因为页面上收集了反馈，就假定系统已经学会。

## 容易踩的坑

格式正确不代表业务判断正确。已有缓存不代表它具备任务所需的粒度和时效。合理的新方案也不代表当前已获得实施授权：调研、需求、编码和上线需要分别说明。

## 怎样验证收益

固定同一批样本与数据快照，比较漏报、误报、人工改判、耗时、模型调用量及人工复核成本。记录边界样本，避免只看明显异常。

可复用原则是让程序处理可复核规则，让模型集中处理真正需要理解的问题。是否更省时或更准确，需要实际对照，不能仅凭架构描述承诺。

# Dividing Work Between Deterministic Software and Language Models

## English

## Separate calculation from judgment

Sending every record to a model is not always useful when a task includes extensive aggregation, comparison, and state evaluation. Conventional software can handle explicit rules. Models can focus on interpretation, synthesis, and incomplete evidence.

This principle is independent of programming language. The relevant question is whether a rule can be defined and checked.

## Generic example: order risk analysis

A workflow collects delivery, outstanding quantity, purchasing, and quality facts, then asks a model to assign risk levels. The output can satisfy its schema and citation requirements while still classifying a completed order as high risk because of a historical issue. Missing priorities and exclusions can cause the error.

Investigate reusable reporting data before collecting everything again. Add missing sources, then let deterministic processing deduplicate, join, apply stable rules, and select candidates. The model receives relevant facts, explains risk, and identifies information that requires confirmation.

Check aggregation carefully. Product-level stock or progress may not establish completion for an individual order. Estimates can support risk signals when their limitations are explicit.

## How AI participates

AI can inspect data descriptions and implementations, identify missing sources, compare definitions, draft rules, and explain candidate exceptions. Business reviewers establish priorities and cases requiring human judgment.

Reviewer comments affect formal analysis only when they enter controlled rules or subsequent inputs. Collecting feedback on a screen does not itself mean that the system has learned from it.

## Common pitfalls

Valid formatting does not prove sound judgment. Existing cached data may lack the necessary granularity or freshness. A sensible proposal does not authorize implementation: investigation, requirements, coding, and deployment are distinct stages.

## Evaluate the benefit

Use the same samples and data snapshot to compare missed risks, false alerts, manual corrections, elapsed time, model usage, and review effort. Include boundary cases rather than only obvious exceptions.

Let software handle explicit rules and reserve models for work requiring interpretation. Claims about speed, cost, or accuracy require an actual comparison.

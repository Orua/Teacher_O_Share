# 业务系统接入 AI 与可靠写入：API、MCP 和业务闭环

## 中文

本文面向希望让 AI 助手使用业务能力的团队，方法适用于不同语言、框架、平台和部署方式。第 13—15 节来自已核对的历史开发、测试和导入记录；业务身份、单号及内部结构已脱敏。前面的流程是可迁移方法，不表示每项保障在历史版本中都已实现。完整中文在前，完整英文在后。

## 1. 明确目标与交付路径

目标是让 Agent 在授权范围内正确查询和操作业务系统，并能解释结果、追踪操作。

```text
明确场景与授权范围
→ 梳理 UI 功能与业务流程
→ 追查源码、数据关系及关联处理
→ 定义 API 契约
→ 实现或复用业务服务
→ 封装 MCP 工具
→ 完成身份与权限接入
→ 做针对性测试
→ 按授权部署、确认并交付使用说明
```

身份与权限应从接口设计阶段同步考虑和实现，不能等到业务开发结束才补上。

## 2. 从 UI 追到业务逻辑

从实际任务开始，例如“查某客户未完成订单”“解释本月销售额”“修改一张单据”。围绕任务检查相关页面，无需一开始遍历整个系统。

| 检查对象 | 需要确认的问题 |
|---|---|
| 查询与详情 | 能查什么？条件如何组合？默认时间范围是什么？ |
| 字段与名称 | 哪些是业务编号，哪些是数据库 ID？数量、金额单位是什么？ |
| 新增与修改 | 必填项、默认值、自动计算、不可修改字段是什么？ |
| 删除与状态 | 是删除、作废还是状态流转？哪些条件下允许？ |
| 业务联动 | 保存后会同步哪些资料、库存、状态、通知或日志？ |
| 权限 | 谁能查看或修改？是否受组织、租户或资料归属限制？ |

UI 是业务发现入口。应继续沿页面事件、请求处理、业务服务、数据访问或外部系统追查，并结合已有源码、接口和测试确认，不必全部通过点击完成。

特别关注“保存之后发生什么”：修改订单可能同时涉及校验、金额重算、库存预占、关联单同步和审计。只更新订单表，并不等于实现完整业务能力。

| 用户动作 | 入口 | 业务处理 | 关联影响 | 权限 | 对应接口 |
|---|---|---|---|---|---|
| 修改订单 | 编辑页保存 | 校验并更新订单 | 重算金额、同步关联状态、留底 | 可编辑目标订单 | `order.update` |

没有 UI 的新功能，通过需求访谈、业务规则和样例建立同类映射。

## 3. API 与 MCP 的分工

API 提供业务能力；MCP 让 Agent 发现并调用这些能力。两者应尽量复用业务服务及权限规则。

```text
网页 / 移动端 / 其他程序 → API 适配层 ─┐
                                    ├→ 业务服务 → 数据库 / 外部服务
AI Agent → MCP 工具适配层 ────────────┘
             各入口采用统一的身份与权限规则
```

MCP 可以调用已有 API，也可以在同一进程内调用业务服务。不强制增加 HTTP 调用或另建微服务，应选择适合现有架构、易于维护的方案。

复杂业务规则放在共用业务服务中；分页适配、参数转换和响应包装可以保留在各入口。

## 4. 先定义契约

每个操作至少说明：

- **用途**：解决什么问题、适用什么场景。
- **输入**：类型、必填条件、默认值、枚举、日期时区及单位。
- **查询规则**：筛选组合、排序、分页、空结果及总数口径。
- **输出**：字段含义及必要的关联 ID、编号、名称。
- **权限**：操作权限、资料范围、敏感字段可见性。
- **副作用**：改变什么，是否涉及事务或外部调用。
- **错误**：区分无资料、无权限、参数错误、状态冲突和能力不可用。
- **重试**：是否可安全重试，写入如何避免重复执行。

可以按列表、详情、统计、新增、修改和状态操作分类，但不必为每张表机械生成全部增删改查。以“审批”“取消”“入库”等业务动作为单位，通常更容易保持业务规则完整。

HTTP API 可以使用 OpenAPI 描述契约，参考文末官方规范。

## 5. 设计 Agent 能正确使用的工具

工具说明应回答“何时用、怎么用、会产生什么结果”。

- 能力较少时，直接提供 `search_orders`、`get_order`、`update_order` 等具体工具。
- 能力较多时，可按业务域拆分，或采用少量入口、操作目录和按需帮助。

通用入口加动态帮助是应用层设计，不是 MCP 的统一要求。具体工具应提供清晰 schema；通用入口也必须具备可靠的操作发现和参数校验机制。

说明需要包含业务语义，例如客户名称是否包含匹配、日期依据创建时间还是交期、是否包含取消订单。

结果保持结构化，包含必要的编号、名称、单位及状态，并区分空结果、失败、无权限和模块不可用。写入工具应明确副作用；需要确认时，确认必须对应本次具体动作和参数。界面提示、模型承诺或工具描述不能代替服务端权限检查。

## 6. 每人独立身份与凭据

各入口应采用一致的身份与权限规则。用户或自动化任务使用可识别、可撤销的独立凭据，不共用高权限身份。

认证方式依据系统边界、客户端能力及适用协议选择。身份来自可信认证结果；业务参数中的用户编号不能覆盖操作者身份。地址中的标识也不能单独作为认证依据。

凭据按需要设置有效期、权限范围和调用限制，并支持轮换。真实凭据不得进入文档、日志、浏览历史或分享链接。跨服务调用采用被目标服务认可的身份或委托机制。

## 7. 每次调用都检查业务权限

认证回答“你是谁”；授权回答“你能对哪些资料做什么”。

```text
验证凭据 → 取得服务端可信身份 → 检查账号状态及凭据范围
→ 检查操作权限 → 检查组织、租户与资料归属
→ 检查敏感字段及业务状态限制 → 执行业务 → 记录结果
```

工具列表可按权限显示，但隐藏工具不能代替执行时授权。能连接 MCP 不代表能调用所有工具。

操作者身份来自可信认证上下文，不得被业务参数覆盖。“负责人 ID”“目标用户 ID”可以作为业务参数，但必须与实际操作者区分，并验证用途。

API 与 MCP 共用身份规则，不代表能把收到的令牌直接透传给任意下游服务。跨服务调用应使用下游认可的凭据或正式委托机制；参见文末 MCP 授权参考。

## 8. 按规模分工并复核

大任务可按职责并行；小任务由一个 Agent 完成即可。

| 角色 | 主要任务 | 交付物 |
|---|---|---|
| 业务梳理 | 检查 UI、用例、数据关系与联动 | 功能与逻辑映射 |
| 接口实现 | 定义契约、复用业务逻辑、编程 | API 与 MCP 实现 |
| 验证 | 对照页面、真实样例与权限 | 验证结果与差异 |
| 主负责人 | 汇总结论、解决冲突、确认范围 | 可交付版本与未完成项 |

分工时明确目录、模块、读写授权和验收要求，减少同时修改同一文件。业务研究默认只读；生产写入、删除、对外发送和部署按已有明确授权执行，委派不扩大权限。

## 9. 三层针对性验证

1. **契约层**：检查参数、必填项、响应结构、错误语义、工具发现与说明。
2. **业务层**：选择直接相关的真实或受控样例，对照页面、业务规则和数据状态；关注筛选、分页、统计口径及写入联动。
3. **权限层**：检查有效和错误凭据、用户绑定、权限不足及跨资料范围访问；涉及多租户时检查隔离。

写入测试优先使用隔离环境：记录初始状态 → 执行 → 读回主记录及关联状态 → 检查审计 → 按计划清理。存在网络重试时，按风险验证幂等性或去重；跨系统操作需要说明部分成功的处理方式。

验证深度按改动和风险决定。普通改动通过一轮针对性验证即可交付，不默认扩展为全站审计。

| 证据 | 可以支持的结论 |
|---|---|
| 构建通过 | 当前实现可构建 |
| 工具可列出、帮助可读取 | 工具发现和说明入口可用 |
| 接口返回成功 | 本次调用返回成功，具体业务结果仍需核对 |
| 业务对照通过 | 已检查场景符合业务规则 |
| 部署确认通过 | 目标环境中的指定能力可用 |

不能把“接口数量齐全”或“返回成功”写成全部业务已验收。

## 10. 部署与使用说明

部署前保留必要备份，确认目标环境，保护现有配置及无关修改。按授权部署已验证的候选版本，并完成一次与改动直接相关的线上确认。

交付说明应包括：完成内容、连接方式、个人凭据取得和撤销方法、可用工具、验证层级、部署状态及剩余限制。

文档同时服务人和 Agent：人能理解业务与权限，Agent 能获取准确参数及调用方式。接口、工具 schema 和说明应同步更新。

## 11. 契约需要同时覆盖业务与执行

一个写入动作的完成条件应同时覆盖输入语义、可信身份、关联变化和可核查结果。任务交接只列“新增了哪些接口”，会漏掉原页面隐含的规则；只列“测试通过”，又无法知道检查了哪条路径。

下文的真实案例说明，复用旧数据访问方法不一定复用了完整业务动作，统一入口也不自动保证每个异常出口都有审计。多执行者的依赖与交付管理集中见[第 04 篇](04_AI协作开发与交付闭环.md)。

## 12. 常见遗漏

- 只按数据库字段做接口，忽略完整业务流程。
- 只检查 UI 表面，未追查后台校验及关联动作。
- API 与 MCP 各写一套规则，逐渐出现行为差异。
- 把 UserID 当作认证，未验证凭据绑定。
- 所有人共用管理员 Key，无法隔离权限或追踪操作者。
- 只限制工具显示，未限制实际调用和资料范围。
- 测试只看成功响应，未读回业务结果和关联状态。
- 文档列出能力，却未说明限制和实际验证范围。

交付标准：助手理解能力，以正确身份调用，并获得符合业务规则的结果。

## 13. 从计件录入页追到接口：字段齐全不等于动作相同

一次计件记录接口补齐任务，要求沿用现有实体的 API/MCP 结构，并以原页面逻辑判断必填项。调查不是从数据表自动生成字段开始，而是依次读取新增页的加载与保存处理、列表权限、已有写入处理器和数据访问方法。

这条调用链揭示了直接收字段的旧入口所缺少的语义：员工必须存在、数量必须有效、日期必须有效，录入身份来自当前用户，数量或单价修改后要重新计算金额。后来用户又明确要求部门必须选择，不能为零。最终约束还要求员工所属部门与传入部门相符；修改时先应用请求中的字段，再校验修改后的对象，避免只验证旧记录。

这里有一个真实的方案修正：早期实现倾向从员工资料自动补部门，后来的业务确认要求显式选择并验证一致性。两者都能生成有值的记录，但表达的业务责任不同。不能把“数据库非空”当作用户已经确认归属，也不能把后来的严格接口规则误写成原 UI 自始如此。

权限负测又发现，未带 key 的列表请求竟然成功。最初有两个候选解释：网关没有挡住请求，或处理器从站点上下文取得了默认用户。修正后的本地对照明确记录无 key 返回 `Code=401`、具备业务权限的身份返回成功；这个结果证明所测入口恢复了认证拒绝，不能据此宣称完成了所有用户隔离审计。

| 验证阶段 | 实际观察 | 结论边界 |
|---|---|---|
| 受控新增、修改、读取、删除 | 两条新增、一条修改、两条删除，最终测试记录为零 | 对应 CRUD 路径成立 |
| 部门缺失或为零、工号无效 | 后续严格校验返回 400 | 业务关联不能靠任意字段填充绕过 |
| 正确部门与员工组合 | 新增、修改、删除通过 | 已测组合有效，不代表历史员工归属问题全部解决 |

测试中也出现过一次假故障：测试脚本使用了宿主 shell 的特殊参数变量名，导致“正确新增”传参不稳定。单独请求成功后，修正脚本并清理其临时记录，再重跑同组测试。这避免把测试端问题修进业务代码。

这次采用共用校验和既有业务/数据访问方法，API 与 MCP 保持适配职责，没有为了接入 AI 再建一套业务微服务。可迁移经验是：沿 UI 追查的是**默认值从何而来、派生值何时重算、关联对象如何验证**，而不只是字段列表。

## 14. 写入已经生效，为什么审计仍不完整

另一轮写接口扩展先完成了受控对象的新增、修改、删除和删除后再修改的检查。用户随后追问原管理页面里的日志。复查发现，MCP 写入口其实已有日志追加调用，所以“完全没日志”不是准确诊断。

真正的问题有两层：旧日志以“新增数量、创建 ID”表达结果，无法清楚区分 UPDATE、DELETE；部分直连 API 异常出口缺少统一兜底。主记录变化成立，不代表日志语义和展示链也完整。

调查沿“写入入口 → 执行结果/异常 → 日志模型 → 最近记录读取 → 管理页面绑定”追踪。修复给日志增加操作类型、影响数量和对象集合，同时保留旧创建字段的读取兼容。页面文件的旧编码使直接文本补丁失败，最终采用后台绑定兼容，并在工具显示中带出动作，而没有强行重写整页。这个取舍减少了无关界面风险，也留下表头未全面现代化的限制。

验证不再只问接口是否成功，而是检查同一测试对象对应的日志：新增、更新、删除都有各自动作；对象删除后再次更新产生失败记录，影响数为零，并有验证错误摘要。本地构建和这些请求通过，测试对象已清理。该轮证据支持审计链补齐，不提供生产全量审计一致性或数据库与文件日志原子提交的证明。

| 最初证据 | 后来补到的证据 | 判断变化 |
|---|---|---|
| 主记录可创建、更新、删除 | 对应动作、对象和结果可读 | 从 CRUD 可用提升到所测操作可追踪 |
| 统一入口已有日志函数 | 异常出口和直连路径需分别核对 | “有日志函数”不是覆盖率证明 |
| 旧页面仍能显示记录 | 旧字段回退与新动作语义兼容 | 展示兼容不应抹掉不同写入的含义 |

在已有系统中，审计页面本身就是业务需求证据。它提供了接口清单没有表达的完成条件。

## 15. 批量导入：一个部门错误最终追到对象重号

一次历史计件导入先完成全量清洗，把无法确认的行留在待处理集合，再顺序提交已确认记录。执行到中途，接口拒绝某些员工的部门。最初看起来是“员工现行部门与历史业务部门不同”，若直接把历史记录改成当前部门，接口也许会放行，却会改变业务事实。

按姓名复核后，发现其中一个对象可以正确写入，另一些仍不行。继续对照本地与服务器名册，才确认同一工号对应不同员工，而写入口主要按工号识别。姓名看起来正确不能消除编号歧义；这也解释了为什么错误表现为部门不匹配。

处理没有用姓名字段绕过服务端校验。经用户确认，先修正本地名册和待导入映射，由管理人员更新服务器对应工号；收到完成消息后再读回服务器资料，确认新号唯一且归属正确。随后以来源行号减去已成功集合，重建剩余清单，而不是从整个失败批次或整个文件重新开始。

续传首批包含改号对象，写入后立即抽查回读；最终按相同期间与部门查询总数，与已确认导入清单一致，待确认集合没有混入。公开文章不保留员工数量、业务总量、姓名或实际编号。

这个案例不能证明接口实现了通用 exactly-once。实际恢复依赖成功行记录、服务器读回和业务映射核对；网络断开造成结果未知时，仍须先查实际落库情况。本次“验证拒绝的行未写入”也不能泛化为所有批量接口都具备全批事务回滚。

批次大小只是当时接口的参数边界。真正可迁移的是三层身份：**源表中的业务对象、服务器唯一标识、已执行来源行**。三者必须同时保持一致，才能避免把对象修正变成重复写入。

# Connecting Business Systems to AI with Reliable Writes

## English

This guide is for teams enabling AI assistants to use business capabilities. Its methods apply across languages, frameworks, platforms, and deployment models. Sections 13–15 draw on checked development, test, and import records, with business identities, references, and internal structures removed. The earlier workflow is transferable guidance, not a claim that every safeguard existed in the historical version. The complete Chinese text precedes the complete English text.

## 1. Define the Goal and Delivery Workflow

The goal is to let agents query and operate business systems within their authorized scope, explain results, and leave a traceable record of operations.

```text
Define scenarios and authorization boundaries
→ Map UI capabilities and business workflows
→ Trace source code, data relationships, and related processing
→ Define API contracts
→ Implement or reuse business services
→ Expose MCP tools
→ Complete identity and permission integration
→ Run targeted tests
→ Deploy as authorized, verify, and deliver usage instructions
```

Design and implement identity and permissions alongside the API contract, rather than adding them after business development is complete.

## 2. Trace the UI to the Business Logic

Start with real tasks, such as finding a customer's outstanding orders, explaining monthly sales, or updating a business document. Inspect the relevant pages without surveying the entire system first.

| Area | Questions to resolve |
|---|---|
| Search and details | What can be queried? How do filters combine? What is the default date range? |
| Fields and names | Which values are business references versus database IDs? What are the quantity and currency units? |
| Create and update | What is required, defaulted, calculated automatically, or immutable? |
| Deletion and status | Is the action deletion, voiding, or a status transition? When is it allowed? |
| Related processing | What records, inventory, statuses, notifications, or logs change after saving? |
| Permissions | Who may view or edit? Do organization, tenant, or ownership restrictions apply? |

The UI is a starting point. Follow page events, request handlers, business services, data access, and external integrations. Use existing source code, APIs, and tests where available; not every step requires clicking through the interface.

Pay particular attention to what happens after saving. An order update may validate fields, recalculate amounts, reserve inventory, synchronize related documents, and record an audit event. Updating the order table alone does not reproduce the complete business operation.

| User action | Entry point | Business processing | Related effects | Permission | API operation |
|---|---|---|---|---|---|
| Update order | Save on edit page | Validate and update order | Recalculate amounts, synchronize statuses, record audit | May edit the target order | `order.update` |

For new capabilities without a UI, build the same mapping from stakeholder discussions, business rules, and examples.

## 3. Separate API and MCP Responsibilities

APIs expose business capabilities. MCP makes those capabilities discoverable and callable by agents. Both should reuse business services and permission rules wherever practical.

```text
Web / Mobile / Other applications → API adapter ─┐
                                                ├→ Business services → Database / External services
AI agent → MCP tool adapter ─────────────────────┘
            Consistent identity and permission rules across entry points
```

MCP may call an existing API or invoke business services within the same process. An additional HTTP request or a separate microservice is not mandatory. Choose an implementation that fits the existing architecture and remains maintainable.

Keep complex business rules in shared services. Pagination adaptation, parameter conversion, and response formatting may remain in the adapters.

## 4. Define Contracts Before Coding

Document at least the following for each operation:

- **Purpose**: the problem it solves and when to use it.
- **Inputs**: types, required conditions, defaults, enums, date/time zones, and units.
- **Query behavior**: filter combinations, sorting, pagination, empty results, and total-count definitions.
- **Outputs**: field meanings and necessary related IDs, references, and names.
- **Permissions**: allowed actions, accessible records, and sensitive-field visibility.
- **Side effects**: changes made, transaction boundaries, and external calls.
- **Errors**: distinguish no data, access denied, invalid input, status conflicts, and unavailable capabilities.
- **Retries**: whether retries are safe and how duplicate writes are prevented.

Operations may be grouped into lists, details, summaries, creation, updates, and status changes. Do not automatically generate every CRUD operation for every table. Business actions such as approve, cancel, or receive stock often preserve rules more effectively than unrestricted field updates.

HTTP APIs can use OpenAPI to describe their contracts. See the official reference at the end.

## 5. Design Tools Agents Can Use Correctly

Tool descriptions should explain when to use a tool, how to call it, and what it will do.

- For a small capability set, expose specific tools such as `search_orders`, `get_order`, and `update_order`.
- For larger systems, organize tools by business domain, or use a small set of entry points with an operation catalog and on-demand help.

A generic entry point with dynamic help is an application design choice, not a universal MCP requirement. Specific tools need clear schemas. Generic tools still need reliable operation discovery and parameter validation.

Explain business semantics: whether customer names use substring matching, whether dates mean creation dates or delivery dates, and whether canceled orders are included.

Return structured results with the necessary references, names, units, and statuses. Distinguish empty results, failures, denied access, and unavailable modules. Write tools must describe their side effects. When confirmation is required, bind it to the specific action and parameters. UI prompts, model promises, and tool descriptions do not replace server-side authorization.

## 6. Give Each User an Independent Identity and Credential

Use consistent identity and permission rules across entry points. Give users and automated tasks identifiable, revocable credentials instead of a shared privileged identity.

Choose authentication according to system boundaries, client capabilities, and applicable protocols. Establish identity from trusted authentication results. Business user identifiers must not override the acting identity, and identifiers in an address do not establish authentication.

Set expiration, scopes, and usage limits as appropriate and support rotation. Keep real credentials out of documents, logs, browser history, and shared links. Cross-service calls need an identity or delegation accepted by the receiving service.

## 7. Enforce Business Permissions on Every Call

Authentication answers who you are. Authorization determines what you may do to which records.

```text
Validate credential → Establish trusted server-side identity → Check account status and credential scope
→ Check operation permission → Check organization, tenant, and record ownership
→ Enforce sensitive-field and business-state restrictions → Execute → Record the result
```

Tool visibility may depend on permissions, but hiding tools does not replace authorization during execution. Connecting to MCP does not grant access to every tool.

The acting identity must come from trusted authentication context and must not be overridden by business parameters. An owner ID or target user ID may be a valid business parameter, but it must remain distinct from the caller's identity and be validated for its intended use.

Shared identity rules do not permit forwarding incoming tokens to arbitrary downstream services. Use credentials accepted by the downstream service or a formal delegation mechanism. See the MCP authorization references below.

## 8. Divide Work According to Scale and Review Results

Large tasks may be divided by responsibility. A single agent is sufficient for small tasks.

| Role | Responsibility | Deliverable |
|---|---|---|
| Business analysis | Inspect UI, use cases, data relationships, and related processing | Capability and logic mapping |
| Implementation | Define contracts, reuse business logic, and write code | API and MCP implementation |
| Verification | Compare pages, representative records, and permissions | Results and discrepancies |
| Lead | Consolidate findings, resolve conflicts, and confirm scope | Deliverable version and outstanding items |

Specify directories, modules, read/write authorization, and acceptance criteria. Avoid simultaneous edits to the same files. Business investigation is read-only by default. Production writes, deletions, external messages, and deployment follow existing explicit authorization; delegation does not expand it.

## 9. Run Targeted Verification at Three Levels

1. **Contract level**: verify parameters, required fields, response structures, error meanings, tool discovery, and documentation.
2. **Business level**: use directly relevant real or controlled examples and compare them against the UI, business rules, and data state. Focus on filtering, pagination, aggregation definitions, and related write effects.
3. **Permission level**: check valid and invalid credentials, user binding, insufficient permissions, and access outside the allowed record scope. Test tenant isolation where applicable.

Prefer isolated environments for write tests: record the initial state → execute → read back primary and related records → inspect audit records → clean up as planned. Where network retries occur, verify idempotency or deduplication according to risk. Explain how partial success is handled across systems.

Match verification depth to the change and its risk. An ordinary change can be delivered after one targeted verification pass; a full-system audit is not the default.

| Evidence | Supported conclusion |
|---|---|
| Build passes | The implementation can be built |
| Tools are listed and help is readable | Discovery and help entry points work |
| API reports success | This call reported success; the business result still needs checking |
| Business comparison passes | The checked scenarios follow the business rules |
| Deployment verification passes | The specified capability works in the target environment |

A complete API list or a successful response does not establish acceptance of all business behavior.

## 10. Deployment and Usage Instructions

Before deployment, retain necessary backups, confirm the target environment, and protect existing configuration and unrelated changes. Deploy the verified candidate as authorized and perform one live check directly related to the change.

The handover should state what was completed, how to connect, how to obtain and revoke personal credentials, which tools are available, the verification level, deployment status, and remaining limitations.

Documentation serves both people and agents. People need clear business and permission explanations; agents need accurate parameters and calling instructions. Update APIs, tool schemas, and documentation together.

## 11. Contracts Must Cover Business and Execution

A write's completion conditions should cover input semantics, trusted identity, related changes, and verifiable results. A handoff listing only new endpoints misses rules implicit in the original page. A statement that tests passed does not identify the exercised path.

The cases below show that reusing data-access methods need not reuse the complete business action, and a common entry point does not automatically audit every failure exit. Dependency and delivery coordination across executors is covered in [Article 04](04_AI协作开发与交付闭环.md).

## 12. Common Omissions

- Building interfaces from database fields without tracing the complete business workflow.
- Inspecting only the UI without tracing backend validation and related processing.
- Duplicating business rules in API and MCP implementations until behavior diverges.
- Treating a UserID as authentication without validating credential binding.
- Sharing an administrator key, preventing permission isolation and caller attribution.
- Restricting tool visibility without enforcing permissions and record scope during execution.
- Checking success responses without reading back business results and related state.
- Listing capabilities without stating limitations and actual verification coverage.

Delivery standard: the assistant understands the capability, invokes it under the correct identity, and obtains a result consistent with business rules.

## 13. Tracing a Piecework Entry Page: Complete Fields Are Not the Same Action

A piecework-record integration task required the existing API/MCP structure and the original UI's required-field logic. Investigation followed page loading and saving, list permissions, existing write handlers, and data-access methods rather than generating an interface from table columns.

The chain exposed semantics missing from the old field-accepting endpoint: the worker must exist, quantity and date must be valid, the recording identity comes from the current user, and changes to quantity or price require amount recalculation. The user later required an explicitly selected, nonzero department. The final constraint also checked that the worker belonged to that department. Updates applied supplied fields before validating the resulting object, rather than validating only its old state.

This was a real design correction. The early implementation favored deriving the department from worker data; later business confirmation required explicit selection and consistency checking. Both approaches produce populated records, but assign different business responsibility. A nonempty database field does not establish confirmed attribution, and the stricter later API rule should not be presented as the UI's original behavior.

A negative permission test then found that a list request without a key succeeded. The initial explanations were a missing gateway check or a default user obtained from site context. After correction, local comparisons recorded `Code=401` without a key and success for an identity with the relevant business permission. This established rejection on the tested path, not a complete isolation audit.

| Verification stage | Observation | Limit |
|---|---|---|
| Controlled create, update, read, and delete | Two creates, one update, two deletes, zero remaining test records | The exercised CRUD path worked |
| Missing or zero department, invalid worker reference | Later strict checks returned 400 | Arbitrary populated fields could not bypass relationship checks |
| Valid worker and department combination | Create, update, and delete passed | The tested combination worked; historical attribution issues were not all resolved |

One apparent failure came from the test harness: a parameter name conflicted with a special shell variable, making the valid-create request unstable. An individual request succeeded. The harness was corrected, its temporary record removed, and the same checks rerun, avoiding an unnecessary business-code fix.

The implementation reused common validation and existing business/data-access methods, leaving adaptation to API and MCP rather than introducing another business microservice. The transferable investigation concerns **where defaults originate, when derived values are recalculated, and how related objects are validated**, not just which fields exist.

## 14. Writes Took Effect, but the Audit Was Incomplete

Another write-interface extension first completed controlled create, update, delete, and update-after-delete checks. The user then asked about the existing administrative log view. Inspection found that the MCP entry already appended log records, so “no logging at all” was not the correct diagnosis.

There were two gaps: the old log represented results as created counts and created IDs, obscuring UPDATE and DELETE, while some direct API exception exits lacked a common logging fallback. A changed primary record did not establish complete audit semantics or presentation.

The investigation followed the write entry, execution result or exception, log model, recent-record reader, and page binding. The repair added operation, affected count, and affected objects while retaining compatibility with old creation fields. A direct text patch failed against the page's legacy encoding. The chosen repair used compatible server-side binding and included the action in tool display rather than rewriting the whole page. This reduced unrelated UI risk but left the headings short of a complete modernization.

Verification now checked logs for the same controlled object: distinct create, update, and delete actions, followed by a failed update after deletion, zero affected records, and a validation-error summary. Local builds and requests passed, and the object was removed. This supports the tested audit path; it does not establish production-wide audit consistency or atomic commitment between database writes and file logs.

| Initial evidence | Added evidence | Changed judgment |
|---|---|---|
| Primary records could be created, updated, and deleted | Corresponding action, object, and result were readable | From usable CRUD to traceable tested operations |
| A common entry had a logging function | Exception exits and direct paths needed separate inspection | A logging function is not proof of coverage |
| The old page still displayed records | Old-field fallback preserved new action semantics | Compatibility must not erase differences between writes |

In an existing system, the audit page is itself business-requirement evidence. It exposes completion conditions absent from an endpoint inventory.

## 15. Batch Import: a Department Error Led to Duplicate Identities

A historical piecework import first cleaned the full input, separated unresolved rows, and submitted confirmed records sequentially. Partway through, the interface rejected some workers' departments. The initial explanation was a mismatch between current employment and historical business attribution. Reassigning historical records to the current department might have passed validation while changing the facts.

Name-based review allowed one object to be written, but others still failed. Comparing local and server directories revealed shared worker numbers belonging to different people, while the write interface identified workers primarily by number. Correct-looking names could not resolve that ambiguity, explaining why the symptom appeared as a department mismatch.

The remedy did not bypass validation through a name field. With user confirmation, local directories and pending mappings were corrected, and an administrator updated the corresponding server references. The agent then read the server data back to establish uniqueness and department consistency. Remaining work was rebuilt by subtracting successful source rows, rather than restarting the whole failed batch or file.

The first resumed batch included corrected identities and was read back immediately. Final counts for the same period and department matched the confirmed import list; unresolved rows remained excluded. Employee counts, business totals, names, and actual identifiers are omitted here.

This does not prove general exactly-once behavior. Recovery relied on successful-row records, server readback, and identity reconciliation. An unknown result after disconnection still requires checking actual persistence. The observed absence of writes for validation-rejected rows also does not imply that every batch interface provides whole-batch transactional rollback.

Batch size was a constraint of that interface. The transferable model has three identities: **the source business object, its unique server identifier, and the source row already executed**. All three must remain consistent so that correcting an identity does not create duplicate writes.
